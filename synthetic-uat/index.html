CONTEXT

My role & context

AI Product Manager & UX Researcher · Contract project at Google

The project examines how people and screenshot-based agents navigate the same cloud billing task.

  • Team size · 7 people
  • Timeline · August 2026 – present
  • My responsibilities · I helped frame the research question, design a shared cloud billing task for people and AI agents, and define how to score saved configurations and compare usability friction across the two flows.

01 / RESEARCH QUESTION

A task can look finished and still be wrong.

A saved cloud budget can monitor the wrong costs, notify the wrong people or trigger on forecast spend when the user intended actual spend. A generic completion event misses those differences.

The study asks whether humans and AI agents run into similar friction, and whether a guided workflow changes where it occurs. The shared task gives both groups a concrete goal without prescribing their clicks.

02 / DESIGN TRADE-OFF

One task, two ways to configure it.

The advanced form keeps related settings visible together. The guided flow asks one question per screen and adds a review step. Task wording, fixture data, surrounding screens and saved configuration stay consistent.

SAME TASK · FICTIONAL BILLING ACCOUNT

Set a $1,000 monthly budget for Atlas. Alert only its project owner when actual spend exceeds 80%.

B / GUIDED QUESTIONS

Decide one step at a time.

01 Which costs should this budget cover?
02 How much can Atlas spend?
03 When should the alert trigger?
04 Who should receive the alert?

A sequence of questions reduces what’s visible at once. It introduces extra navigation and makes the review step important for catching dependencies.

Illustrative walkthrough. Both prototypes save the same budget configuration.

What the comparison can isolate. The two flows change several things together, including navigation, hierarchy and wording. A difference would justify investigating the guided experience as a whole. A follow-up experiment could isolate the effect of a single change.

03 / EVALUATION

Score the outcome, then inspect the path.

The same evaluator checks the saved configuration for both interfaces. Recipient accuracy comes from the set of people who would actually get an alert, since different controls can lead to the same recipients.

Screen-by-screen comparisons would favor whichever design splits the task into more pages. Comparing friction by setting makes it possible to ask where people and agents struggle with scope, alert rules or recipients across both versions.

Agents interact through screenshots, mouse and keyboard. The platform logs actions and distinguishes a bad configuration from interruptions such as a timeout or loop.

PILOT

Pilot scope

The pilot is designed to compare people and screenshot-based agents on the same budget setup task in an advanced form and a guided flow.

  • Human sessions · Use the same task prompt and fictional billing data across both interfaces.
  • Agent runs · Use screenshots and browser actions to complete the same task.
  • Comparison · Check saved configurations for errors and review where each group backtracks or stalls, especially around budget scope, alert rules, and recipients.

04 / LIMITS & NEXT STUDY

Treat agreement as something to measure.

The prototype supports the comparison. The available materials document the study design and implementation, with no comparative results reported here.

A follow-up study could compare configuration errors and backtracking across both versions. Disagreement matters: a model may misread a visible control that a person understands, while a person may hesitate over the consequences of sending an alert. That distinction determines which findings need direct human follow-up.

EXHIBIT 05 / IMPLEMENTATION

Keep the experiment interpretable.

The interface stores the assigned version on the session. Both variants use the same configuration shape and evaluator. Saved configurations are scored independently from whether the application accepted them, so a valid budget can still fail the assigned task.

The research console supports session creation, event inspection, re-scoring and export. Agent action records include failures such as timeouts or invalid actions. This helps separate an interaction failure from an incorrect budget decision.

EXHIBIT 06 / REFLECTION

What would change the design direction?

If both groups miss the same recipient dependency, that would motivate testing how scope and recipient consequences are explained. If only agents miss it, the next investigation should inspect perception and action traces before generalizing the result to people.

If the guided flow improves accuracy but takes longer, the product decision depends on the cost of a wrong configuration and the needs of frequent users. Completion time and final accuracy should be interpreted together.
